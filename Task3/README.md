# Требования к внешним интеграциям PropDevelopment  

## Общая архитектурная модель интеграции

Внешняя платформа «Умный дом» интегрируется с PropDevelopment через выделенный сервис-адаптер `SmartHome Service`.

### Принципы:
- Мобильное приложение никогда не взаимодействует напрямую** с партнёром.
- Внешние вызовы выполняются только через backend PropDevelopment.
- `SmartHome Service` выступает в роли:
  - anti-corruption layer;
  - точки централизованной безопасности;
  - адаптера контрактов партнёра.

## 1. Требования к безопасности

### Сетевой периметр и изоляция
1. Все внешние запросы к партнёру выполняются только через egress-gateway / firewall.
2. В кластере используется принцип deny-by-default для egress-трафика.
3. Для внешних интеграций применяется allowlist доменов/IP и портов.
4. Внутренние взаимодействия сервисов защищены mTLS.

### Транспортное шифрование
1. Используется TLS версии 1.2 и выше. 
2. Сертификат партнёра проверяется по цепочке доверия и SAN. 
3. При возможности используется certificate pinning. 
4. Чувствительные данные:
   - в транзите - шифруются (TLS);
   - в покое - шифруются на уровне хранилища и/или приложения.

### Управление секретами
1. Все секреты (HMAC-ключи, токены, доступы и тд) хранятся исключительно в Vault. 
2. Секреты не размещаются в:
    - Kubernetes manifests;
    - ConfigMap;
    - исходном коде. 
3. Поддерживается регламентированная ротация секретов без простоя сервисов.

### Аудит и наблюдаемость
1. Все операции фиксируются в централизованном аудите:
    - пользователь;
    - объект (домофон / шлагбаум);
    - операция;
    - результат;
    - timestamp;
    - correlation ID.
2. Логи и аудит защищены от несанкционированного удаления.
3. Все внешние вызовы поддерживают traceId.

### Защита от злоупотреблений
1. Реализован rate limiting:
    - по пользователю;
    - по устройству;
    - по дому или подъезду.
2. Все команды управления поддерживают идемпотентность.
3. Для внешних API настроены:
    - таймауты;
    - ограниченные ретраи;
    - circuit breaker.

## 2. Аутентификация и авторизация

Рекомендуемый вариант:
- OAuth 2.0 Client Credentials
- Access Token в формате JWT

Требования:
- Токены короткоживущие (5–15 минут).
- Используются ограниченные scopes, например:
  - `intercom:open`
  - `gate:open`
  - `intercom:events:read`

Альтернативный вариант (если OAuth недоступен):
- HMAC-подпись запросов (HMAC-SHA256)
- Подпись включает method, path, body hash, timestamp, nonce.

### Персональные и биометрические данные
- PropDevelopment не хранит биометрические шаблоны и изображения, если это не требуется бизнесом.
- Хранятся только:
  - идентификаторы пользователей;
  - идентификаторы профилей у партнёра;
  - события доступа.
- Применяется принцип минимизации персональных данных.

## 3. Организация взаимодействия между системами

### События от партнёра
Поддерживаются:
- HTTPS-взаимодействие
- Webhook-уведомления (предпочтительно)
- Polling

### Надёжность
- Все операции управления идемпотентны.
- Webhook-события имеют `eventId`.
- Поддерживается версионирование API (`/v1`, `/v2`).

## 4. Контракты и совместимость

1. Все API партнёра описаны через **OpenAPI / JSON Schema**.
2. Контракты версионируются.
3. Изменения партнёра не должны ломать текущие интеграции:
   - backward compatibility;
   - grace period.
